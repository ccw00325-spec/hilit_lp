> ### 🔄 SRS v3.0 반영 — 이 태스크에서 바뀐 것 *(2026-09-01)*
> **필터 2단** — 공개범위 필터가 `전체 / Public / Private` 3값으로 줄었다(그룹 값 삭제).
>
> **기준 문서**: `SRS/[SRS]hilit-SRSv2.0-nextjs.md` **v3.0** · `PRD/HILiT_PRD_v0_2.md`

> 🔀 **FR-033(프로필 이중 뷰)을 흡수했다** *(축약 2026-09-01)* — 둘 다 **같은 RLS 경계 · 같은 배지 컴포넌트 · 같은 성능 임계(p95 ≤ 400ms)** 를 공유하는 Query다. 🔴 **그룹 삭제로 조회자 유형이 4 → 3으로 줄면서** 이중 뷰가 단독 태스크일 근거가 약해졌다. `FR-033` 은 폐번이며 이 문서를 가리킨다.
>
> 🔴 **다만 함수는 여전히 둘이다** — `listMyRecords`(소유자) / `getProfile`(타인). 한 함수에 `if (isOwner)` 분기를 넣으면 **SC-4.4(개수에도 미포함)를 실수로 깨뜨리기 쉽다**. 태스크를 합치는 것과 함수를 합치는 것은 다르다.

## 🎯 Summary
- 기능명: **[FR-032] 내 기록은 내가 전부 보고, 남에게는 흔적조차 없다**
- 목적: **Gate B(기록 공간 수용성)가 판정할 "기록 공간"을 만들고, 동시에 REQ-NF-009의 가장 어려운 조항을 만족한다.**

> 🔴 **이 화면이 D4의 결과물이다.**
>
> 앞의 모든 태스크는 *"공개하지 않아도 기록이 남는다"* 를 **가능하게** 했다. 이 화면은 그 기록이 **쌓인 것을 사용자가 실제로 보는 유일한 자리**다. **Gate B가 판정하는 것은 기술이 아니라 이 화면이 주는 느낌**이다.
>
> 🔺 **그래서 "목록이 나온다"만으로는 이 태스크가 끝나지 않는다** — SC-6.4(D30 기록 3편 이상 코호트)가 이 화면의 실질 지표다.

> 🔴 **"안 보여준다"와 "없는 것처럼 보인다"는 다르다** *(← FR-033)*
>
> REQ-NF-009: *"권한 없는 자원은 **응답에서 완전히 제외**해야 하며, **건수·존재 여부를 유추할 수 있는 정보를 반환해서는 안 된다**."*
>
> 흔한 구현은 목록만 거르고 **개수는 전체로 센다.** 그러면 *"기록 27개"* 인데 3개만 보이는 프로필이 나오고, **비공개 24건의 존재가 노출된다.** SC-4.4가 정확히 이 지점을 검사한다.
>
> 🟢 **RLS가 이 문제를 구조적으로 푼다** — `count(*)` 도 정책의 영향을 받으므로 **애플리케이션이 따로 신경 쓸 필요가 없어진다.**

## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 비공개 기록이 내게는 보인다** *(D4)*
- **Given**: `private` 기록 12건
- **When**: 마이페이지를 엶
- **Then**: 🔴 **12건이 전부 보인다.** 소유자 뷰에서는 공개 범위가 가시성을 제한하지 않는다

**Scenario 2: 공개 범위가 배지로 표시된다** *(SC-4.3 · ADR-4)*
- **Given**: 세 가지 범위가 섞인 목록
- **When**: 격자를 확인함
- **Then**: 🔴 **글자 배지로 표시되고 영상을 가리지 않는다**

**Scenario 3: 종목·공개 범위로 거를 수 있다** *(SC-4.5)*
- **Given**: 여러 종목의 기록
- **When**: 필터를 적용함
- **Then**: **해당 조건의 기록만 남는다.** 두 필터를 함께 적용할 수 있다

**Scenario 4: 날짜별로 쌓인 것이 보인다** *(REQ-FUNC-020)*
- **Given**: 3개월간의 기록
- **When**: 타임라인 뷰를 봄
- **Then**: **날짜별 축적**이 확인된다. 🔴 **"쌓였다"는 감각이 Gate B의 판정 대상이다**

**Scenario 5: 400ms 안에 응답한다** *(REQ-NF-005)*
- **Given**: 기록이 많은 계정
- **When**: 목록을 조회함
- **Then**: **p95 ≤ 400ms**. 🔺 **RLS 정책이 걸린 쿼리의 성능을 인덱스로 받쳐야 한다**(CT-001)

**Scenario 6: 원본이 삭제된 기록도 보인다** *(FR-004)*
- **Given**: 원본을 지운 기록
- **When**: 목록을 봄
- **Then**: 🔴 **정상 표시되고 재생된다.** `source_video_id` 가 `NULL` 이어도 기록은 온전하다

**Scenario 7: 타인에게는 Public만 보인다** *(← FR-033 · SC-4.4)*
- **Given**: Public 3건 · Private 24건인 사용자
- **When**: 완전한 타인이 프로필을 봄
- **Then**: **3건만 보인다**

**Scenario 8: 개수도 3이다** *(← FR-033 · REQ-NF-009 · SC-4.4)*
- **Given**: 위와 같은 상황
- **When**: 기록 수를 확인함
- **Then**: 🔴 **"3"이다.** *"27"* 이나 *"3 / 27"* 이 아니다. **개수 하나가 비공개 24건의 존재를 알려준다**

**Scenario 9: 팔로워라고 더 보이지 않는다** *(← FR-033 · 규칙 8)*
- **Given**: 팔로워인 사용자
- **When**: 프로필을 봄
- **Then**: 🔴 **Public 3건만.** 팔로우는 가시성을 바꾸지 않는다

**Scenario 10: 조작된 요청이 통하지 않는다** *(← FR-033 · SC-4.F1)*
- **Given**: 비공개 기록의 ID를 직접 지정한 요청
- **When**: 조회를 시도함
- **Then**: 🔴 **우회 성공 0건**이고 **`visibility_denied` 감사 로그가 남는다.** 기록률 **100%**

**Scenario 11 (실패): 애플리케이션에서 세지 않는다** *(← FR-033)*
- **Given**: 집계 구현
- **When**: 코드를 확인함
- **Then**: 🔴 **`count(*)` 가 RLS가 적용된 쿼리로 실행**된다. **전체를 가져와 필터링 후 세는 구현은 성능도 나쁘고 반드시 새어나간다**

**Scenario 12 (실패): 두 뷰를 한 함수로 합치지 않는다**
- **Given**: 태스크가 하나로 합쳐졌다는 사실
- **When**: 구현을 검토함
- **Then**: 🔴 **`listMyRecords` 와 `getProfile` 은 여전히 별도 함수다.** 한 함수에 `if (isOwner)` 분기를 넣으면 **SC-4.4를 실수로 깨뜨리기 쉽다** — 태스크를 합치는 것과 함수를 합치는 것은 다르다

## ⚙️ Technical & Non-Functional Constraints
- 🔴 **소유자 뷰와 타인 뷰의 함수를 분리** — 태스크는 하나지만 **함수는 둘**이다
- 🔴 **RLS가 유일한 진실 원천** *(← FR-033)* — 애플리케이션 필터는 이중 방어이지 대체가 아니다
- 🔴 **집계도 RLS를 통과** — 이것이 SRS §4.2가 *"SC-4.4를 구조적으로 해결"* 이라고 표현한 이유다
- 🔺 **존재하지 않는 사용자 vs 접근 불가 사용자의 응답이 같아야 하는지 `[TBD]`** — 다르면 계정 존재 여부가 유추된다
- 🔺 **팔로워·팔로잉 수의 가시성이 `[TBD]`** — 요구사항에 명시가 없다
- 감사 로그 기록률 100% — 누락이 있으면 REQ-NF-009 미충족
- 🔴 **RLS 하에서 소유자는 전부 본다** — 정책이 소유자 조건을 포함해야 한다(CT-003)
- 🔺 **인덱스가 성능을 좌우** — 사용자 · 종목 · 공개 범위 · 날짜 조합 (CT-001)
- 🔺 **SC-6.4(D30 기록 3편 이상)의 집계 위치가 `[TBD]`** — 이 조회가 아니라 분석 파이프라인 소관일 수 있다
- 열거형 확장 패턴 준수 — 종목 추가 시 코드 변경 최소화(REQ-NF-015)
