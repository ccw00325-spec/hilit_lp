> **다른 게이트와 성격이 같다** — 상대가 있는 계약이고, 사내에서 결심해도 상대가 승인하지 않으면 열리지 않는다. 완료 판정은 **계약 체결 + 테스트 결제 성공**이다.

## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 정기결제가 지원된다**
- **Given**: 후보 대행사
- **When**: 구독 상품을 등록함
- **Then**: 🔴 **월 자동 갱신이 동작한다.** 되지 않으면 매월 사용자가 수동 결제해야 하고 이탈이 발생한다

**Scenario 2: webhook이 신뢰할 만하다**
- **Given**: 테스트 결제
- **When**: webhook 수신을 확인함
- **Then**: **재전송·서명 검증이 지원된다.** FR-043의 멱등 설계가 성립하려면 결제 ID가 안정적이어야 한다

**Scenario 3-b: 가변 금액 청구가 된다** *(v0.5 · 🔴 후불의 전제)*
- **Given**: 저장된 결제 수단 · 이번 달 종량 사용액(매달 다름)
- **When**: 서버가 청구를 개시함
- **Then**: 🔴 **사용자 개입 없이 청구가 성공한다.** 🔴 **이것이 안 되면 후불 종량을 구현할 수 없고, PRD v0.5의 구독 추가 사용분 설계를 되돌려야 한다**

**Scenario 3-c: 청구 실패가 통지된다** *(v0.5 · AF-18)*
- **Given**: 만료된 카드
- **When**: 후불 청구가 실패함
- **Then**: **실패 사유가 webhook으로 도착한다.** 통지가 없으면 미납을 **다음 청구 때까지 모른다**

**Scenario 3: 선불 충전이 사용량으로 이어진다**
- **Given**: 🔴 **추가 업로드 1편 결제**(금액 [TBD Q25])
- **When**: 전체 왕복을 확인함
- **Then**: `UsageLedger` 에 3편 + `expiresAt` 30일이 기록된다

**Scenario 4: 환불 정책이 문서화된다**
- **Given**: 부분 사용 후 환불 요청 상황
- **When**: 정책을 확인함
- **Then**: 🔴 **처리 규칙이 문서로 있다.** 없으면 FR-042의 사용량 되돌림이 임의 판단이 된다

**Scenario 5: 게이트 미승인이 서비스를 막지 않는다**
- **Given**: `payment-vendor` 가 `PENDING`
- **When**: 빌드·배포를 수행함
- **Then**: 🟢 **결제 경로만 빠지고 무료 경로는 동작한다.** 다른 게이트(`MINOR_POLICY`)와 달리 **가입 자체를 막지 않는다**

## ⚙️ Technical & Non-Functional Constraints
- 🔴 **정기결제 지원이 탈락 기준** — 일회성만 되면 구독 상품이 성립하지 않는다
- 🔴 **카드 정보를 우리가 보관하지 않는 방식** — PCI 범위를 만들지 않는다
- 🔺 **심사 기간이 일정에 든다** — 개발 완료와 무관하게 시간이 걸린다
- 🔺 **환불·취소 정책** — 사업·법무 결정. FR-042·FR-043의 미결을 여기서 닫는다
